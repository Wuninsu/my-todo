## Security Hardening — Authorization & Policies ✅
_Cross-cutting pass across Phases 1/3/4, done in response to a direct ask: "properly gate the system," no user reads/edits another user's data, admin always lands on the admin overview._

- [x] Added real Laravel Policies (auto-discovered, no manual registration needed): [TodoPolicy](app/Policies/TodoPolicy.php), [TodoListPolicy](app/Policies/TodoListPolicy.php), [DevicePolicy](app/Policies/DevicePolicy.php), [UserPolicy](app/Policies/UserPolicy.php) (`viewAny`/`view`/`update`/`delete`/`restore`, admin-only, `delete` also blocks self-delete)
- [x] Converted the per-record mutate actions (edit/delete/toggle/reorder todo; rename/delete list; revoke device; admin view/edit/delete/restore user) from relationship-scoped queries (`Auth::user()->todos()->findOrFail(...)`) to **global lookup + `$this->authorize()`**, so the Policy is the actual gate, not incidental query scoping. Touched: [Dashboard.php](app/Livewire/Main/Dashboard.php), [SidebarLists.php](app/Livewire/Main/SidebarLists.php), [ProfileIndex.php](app/Livewire/Main/ProfileIndex.php), the three admin `Admin\User*` components
- [x] Fixed a real IDOR gap: `Dashboard`'s `todo_list_id` validation was `exists:todo_lists,id` with no ownership check — a tampered Livewire payload could reassign your todo to another user's list (list would still only be visible to its real owner, but the row itself would be silently orphaned into someone else's list). Now `Rule::exists('todo_lists', 'id')->where('user_id', Auth::id())`
- [x] Admin self-delete: policy owns the rule (`delete` returns false when `$model->id === $user->id`); the component catches `AuthorizationException` to keep the existing friendly flash message rather than a raw 403 page — single source of truth, UX unchanged
- [x] Fixed login/register/root routing: previously **everyone** (including admins) landed on the public marketing page (`/`) after auth, since `redirect()->intended('/')` had no role awareness and `/` never checked auth state. Now: `Login`/`Register` redirect to `admin.dashboard` for admins and `dashboard` for everyone else (still respecting Laravel's `intended()` deep-link behavior), and visiting `/` while already authenticated redirects the same way instead of showing the landing page again
- [x] Incidental fix: `request()->session()->regenerate()` in `Login`/`Register` doesn't work when the component is exercised via `Livewire::test()` directly (no HTTP-kernel-attached session on the `Request` object) — switched to the `session()` helper, which resolves the session driver from the container instead. Behaves identically in production, but this is what made the login flow testable at all
- [x] 12 new tests: [PolicyTest.php](tests/Feature/PolicyTest.php) (direct `Gate::forUser()` checks per policy), [AuthRedirectTest.php](tests/Feature/AuthRedirectTest.php) (root + login redirect targets by role), plus cross-user assertions added to `DashboardTest`, `SidebarListsTest`, `ProfileTest`
- **Note on testing Livewire authorization**: Livewire's test harness (`RequestBroker::temporarilyDisableExceptionHandlingAndMiddleware`) deliberately lets `AuthorizationException` go through normal Laravel exception handling instead of re-throwing it to the test — so `expect(fn () => ...)->toThrow(AuthorizationException::class)` doesn't work here (unlike `ModelNotFoundException`, which does bubble up raw). The correct pattern is to call the action and then assert the record/state is unchanged, which is also just a better test since it verifies behavior, not implementation.
- **Not done / out of scope for this pass**: no policy on `Tag` (nothing currently takes a client-supplied tag ID to mutate — tags are only ever created/attached through the authenticated user's own scoped relation, so there's no IDOR surface yet; add one if that changes) — Sidebar filter/list-id UUID lookups were already safely scoped by `user_id` in the query itself and didn't need conversion. **Superseded below** — the Tag Management screen added afterward introduced exactly that mutate-by-ID surface, so [TagPolicy](app/Policies/TagPolicy.php) now exists.

## Dark Mode Visibility Audit ✅
_Systematic pass fixing every place a component silently stayed in Bootstrap's light-mode styling despite the app being in dark mode._

- [x] Root cause: the app uses its own `data-theme` attribute + CSS variable system, but several native Bootstrap components (`.modal-content`, `.dropdown-menu`, offcanvas, `.table`, `.btn-close`, form controls, `bg-body-tertiary` badges) read from *Bootstrap's own* `--bs-*` variables, which only switch under `data-bs-theme="dark"` — an attribute this app never sets. Anything not explicitly bridged to `--app-*` stayed light internally.
- [x] Fixed: modal text color, mobile sidebar (offcanvas) text color, table body text + border color (`.app-table`), the modal close-button icon (invisible black X on a dark modal — bridged `--bs-btn-close-filter`), all plain `.form-control`/`.form-select`/`.form-check-input` elements (most inputs in the app don't carry the custom `.app-input` class), `.form-label`/`.form-check-label` text color, and `.bg-body-tertiary` badges (due-date/list/tag chips on every todo card) which had a genuine low-contrast gray-on-gray problem, not just a style mismatch.
- [x] Left alone: `alert-success`/`alert-danger` and `bg-*-subtle` status badges — checked their actual color pairs; self-contained and legible regardless of theme, just stylistically light-on-dark. Cosmetic only.

## Service Layer + Crash-Resilient Actions ✅
_Requested directly: "move all business logic from livewire components to a dedicated services, livewire component should only validate and put services call in try catch blocks and log error to a custome channel, create a global tryAction trait then use; so that app does not crash."_

- [x] **[App\Traits\TryAction](app/Traits/TryAction.php)** — the global trait. `$this->tryAction($closure, $failureMessage)` wraps a service call: on success, returns the closure's return value (so redirects like `UserEdit::update()`'s still work — the closure returns the `RedirectResponse` and the component method `return`s the trait call). On failure it never lets the exception escape the component: `AuthorizationException` → generic "You do not have permission to do that." toast; the new `ActionNotAllowedException` (see below) → its own message verbatim; anything else → the caller-supplied `$failureMessage`. Every branch logs to the `services` channel first.
- [x] **New `services` log channel** (`config/logging.php`) — a `daily` driver writing to `storage/logs/services-{date}.log`, separate from `laravel.log`, so action failures are easy to find without wading through framework noise. Already gitignored (Laravel's stock `storage/logs/.gitignore` covers it).
- [x] **New [App\Exceptions\ActionNotAllowedException](app/Exceptions/ActionNotAllowedException.php)** — a marker for *expected* business-rule violations ("the default list can't be deleted," "system tags can't be edited," "you can't delete your own account") as opposed to bugs. Services throw it with the exact user-facing message; `TryAction` shows that message directly instead of a generic one, and logs it at `notice` level rather than `error`. This is what let every existing exact-wording toast test (e.g. `'System tags cannot be edited.'`) keep passing unchanged through the refactor.
- [x] **9 new service classes** under `app/Services/`, one per business domain, each holding the create/update/delete/authorize logic that used to live in the component: `TodoService`, `TodoListService`, `TagService`, `DeviceService`, `ProfileService`, `TrashService` (the four-model polymorphic restore/forceDelete Trash already did, unchanged behavior, just relocated), `UserService` (admin), `AlertService` (notification read/clear), `AuthService` (login/register — `AuthService::register()` still creates the default "My Tasks" list the same way registration always did). A tenth, `AlertGenerationService`, was pulled out of the `todos:generate-alerts` console command for the same reason even though it isn't a Livewire component — the command is now a 15-line wrapper that logs to the same `services` channel on failure.
- [x] **Authorization moved into the services**, using `Gate::authorize(...)` instead of the component's `$this->authorize(...)` — policies are unchanged, only *where* they're invoked from moved, so every `AuthorizationException` a cross-user attempt used to throw is now thrown from inside a service and caught by `TryAction` instead of bubbling into a 403 page.
- [x] **10 Livewire components refactored** to be validate-then-delegate: `Dashboard`, `SidebarLists`, `Tags`, `ProfileIndex`, `Trash`, `Admin\UserIndex`, `Admin\UserEdit`, `AlertCenter`, `ThemeToggle`, `Auth\Login`, `Auth\Register`. Each action method now does `$this->validate()` (when there's form input) then `$this->tryAction(fn () => ..., 'message')`. Services are pulled in via Livewire's method-injection (`public function save(TagService $tags)`), not constructed manually.
- [x] **`layouts.auth` gained the toast + confirm-dialog partials** it was missing — without them, a caught login/register failure would `dispatch('toast', ...)` into a page with nowhere to show it. Small gap, closed as part of making resilience actually visible everywhere, not just on authenticated pages.
- [x] **A real ordering bug caught mid-refactor by re-reading my own diff, not by a failing test**: in the first pass, `SidebarLists::save()` had its success-path `reset()` + toast *after* the `tryAction(...)` call instead of inside its closure — meaning a failed save would still silently reset the form and show a success toast. Fixed by moving all success-path side effects inside the closure (the pattern every other method already followed). Existing tests didn't catch this because they don't assert "no success toast on failure" — worth remembering next time a closure-wrapping refactor like this happens.
- [x] 3 new tests in [TryActionTest.php](tests/Feature/TryActionTest.php) proving the actual guarantee end-to-end: a service throwing `ModelNotFoundException` produces an error toast and a 2xx response instead of an uncaught exception; that failure lands in `storage/logs/services-*.log` specifically (not the default log); a cross-user `AuthorizationException` produces the generic permission toast instead of a 403. Plus a new toast-message assertion added to the existing "default list can't be deleted" test. Full suite: 119/119 passing (up from 116 — no existing test needed to change, only additions).
- [x] Verified in a real browser end-to-end after the refactor (Playwright): login, quick-add, tag create, trash/profile/admin-users pages all load with zero console errors.
- **Scope boundary, deliberate**: `Admin\Overview` (stat counts) and `Admin\UserView` (a single authorize + display) were left alone — both are pure reads with no mutation and no business rule to enforce, so there's nothing to move to a service and nothing that should be silently caught (a broken stats query should surface as a real error, not a swallowed blank page). `Welcome` and `Actions\Logout` are equally thin and untouched for the same reason.
